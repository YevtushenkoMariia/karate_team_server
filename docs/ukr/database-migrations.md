# Міграції бази даних

Baseline-міграція згенерована зі `prisma/schema.prisma`. Підтримуйте схему й
baseline узгодженими: попередній ланцюжок міграцій створював ключі `SERIAL`,
тоді як поточна схема використовує UUID.

Для `prisma migrate dev` задайте `SHADOW_DATABASE_URL` окремої тимчасової
PostgreSQL-бази. Вона не повинна вказувати на базу застосунку чи production.
`prisma.config.ts` використовує цю змінну, коли Prisma створює та скидає
shadow-схему.

## Повторне створення baseline для production

Зробіть резервну копію production і перед baseline перевірте, що таблиці,
колонки, enum-значення, індекси та UUID-типи відповідають baseline. Старі
міграції вже були застосовані в production, тому однієї команди
`prisma migrate resolve --applied 0_init` недостатньо: вона додає запис про
baseline, але не видаляє й не узгоджує старі записи в `_prisma_migrations`.
Узгодження цієї історії має бути окремою перевіреною операцією в production,
перш ніж запускати `migrate deploy`. Не запускайте старий SQL міграцій проти
наявної бази.
